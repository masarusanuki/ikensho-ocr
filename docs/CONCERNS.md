# 主治医意見書OCR：懸念事項と、政府系クラウドについて

この道具を使う前に知っておいてほしいことを、一か所にまとめたものです。
実測で分かっている弱点を、隠さずに書いています。

技術的な経緯や、試して駄目だった方法の記録は
[開発メモ](devnotes.html)にあります。

## 前提：この道具は「人が確認する」ことを前提に作ってある

紙の主治医意見書を読み取り、人が確認して、データにする道具です。
**自動で処理を完結させる使い方は想定していません。**

設計の要は3つです。

1. **項目107のうちチェック欄が186個**を占めるので、そこを画像処理で確実に読み、
   文字欄52個だけをOCRに任せた
2. **読んだ値は必ず人が確認する。** 確信度で色分けし、要確認だけを絞り込め、
   該当箇所を原本で拡大できる画面を用意してある
3. **データを端末の外に出さない。** ブラウザ版は端末内で完結し、
   単一HTMLファイル版はオフラインで動く

3番目が、以下の政府系クラウドの話に直接かかわります。
**いま成り立っている「外に出さない」という前提は、つなぎ先を増やすと崩れます。**

## 読み取りは完全ではない

いずれも正解データと照らした実測値です。**□ひとつを1件として数えています。**

| 正解データ | チェック欄 | 文字欄 |
|---|---|---|
| 100通（18,600枠） | 99.08% | 88.4% |
| 1,000通から64通（4,895枠） | 89.36% | 56.12% |

同じ道具でこれだけ差が出ます。後者は Word入力と手書きが混ざり、汚し方が強いデータです。

チェック欄は、印の書き方によっても大きく変わります（100通・13通りの書き方）。

| 印の書き方 | 正解率 | 件数 |
|---|---|---|
| レ点 / ■ / ×印 / 薄い点 / レ（活字） | 100% | 1,546 |
| チェック ✓ | 99.20% | 249 |
| 斜め線 | 97.96% | 49 |
| 塗りつぶし | 97.43% | 272 |
| 丸囲み | 97.27% | 183 |
| 二重線で訂正 | 82.98% | 47 |
| **枠外にはみ出した印** | **45.61%** | 57 |

## とくに弱いところ

**取り込みの品質が、そのまま精度になります。**
1,000通を読みやすさの4段階で分けて測ると、崩れているのは1種類に集中していました。

| 読みやすさ | チェック欄 | 文字欄 | 1,000通中 |
|---|---|---|---|
| 活字 | 86.5% | 84.2% | 350通 |
| 標準 | 81.6% | 84.2% | 204通 |
| 達筆（連綿・寝せ字） | 78.1% | 39.7% | 227通 |
| **汚い（つぶれ・重なり）** | **66.4%** | **16.1%** | 219通 |

汚いスキャンの文字欄は16.1%で、**実質読めていません**。
これはしきい値の調整では直らない見込みで、
200dpi以上・つぶれない設定での取り込みをお願いするのが一番効きます。

残る2つも書いておきます。

- **枠外にはみ出した印は45.6%。** 枠の中にインクが無く、外のインクは
  隣の欄の手書きと見分けが付きません。1通単位で見分ける層が別に要ります
- **地の汚れが多い紙で誤検出が集中する。** 100通での誤検出117件のうち
  79件が3通に集まっていました

## 正解データそのものの限界

**上の数字はすべて「合成された正解データに対しては」という但し書きが付きます。**

2種類とも、印の種類や汚し方を振って生成されたものです。
実際の紙とは傾向が違う可能性があります。

- 印の種類は13通りだが、実際の医師の書き方はもっと幅があるはず
- 「枠外はみ出し」は生成の規則（枠の右下0.55〜0.95から描く）に沿ったものだけ
- 文字の正解値は欄によって粒度が違う。医療機関名は法人名を含まない一方、
  様式には法人名も書かれている（読みの方が忠実でも不正解に数えられる）

**実データでの検証がまだです。ここが次にやるべきことだと考えています。**

## 作りの上の懸念

**同じ判定を Python 版とブラウザ版の2つ持っています。**
データ（項目定義・テンプレート・辞書）は1つですが、実装は2つあります。
片方だけ壊れていた例が実際に複数出ました（文字クラスのハイフン、CSVの列の並び、
単一HTML版だけファイルが入っていないなど）。
**突き合わせを自動で回す仕組みがまだありません。**

**テンプレートの座標は、目で見て合っていても違うことがあります。**
実際、記入欄の高さと中央寄せの向きを取り違えていて、年齢欄が12.5%しか
読めていませんでした（直した後は54.2%）。
**座標を決めたら必ず測る**という手順が要ります。

**生成AIで文章を直す機能は、既定で切ってあります。**
条件を3通り変えて測りましたが、一度も精度が上がらず、
読み崩れた文に**書かれていない言葉を足す**ことがありました。

```
読み  疼痛評価を続し、 山要に血じて処方調整
校正  疼痛評価を続し、山要に血圧を測って処方調整   ←「血圧を測って」は原本に無い
```

**崩れた読みは見れば誤りと分かりますが、生成された文章は見ても分かりません。**
診療記録では後者の方が危険なので、規則と辞書（1,545語）だけで直しています。

## 源内（デジタル庁の生成AI基盤）につなぐ場合

**受け口は作ってありますが、既定では閉じています**（`ikensho serve --gennai` で開く）。
開けるかどうかは技術の問題ではなく、運用の取り決めの問題です。

開くと、読み取った結果が源内側に渡ります。中身はこうです。

| 渡るもの | 例 |
|---|---|
| 氏名・ふりがな | 佐藤芳江 / さとうよしえ |
| 生年月日・年齢 | 昭和5年8月16日、96歳 |
| 住所・郵便番号・連絡先 | 茨城県土浦市下高津3-7-12 |
| 傷病名・経過・特記事項 | 脳梗塞後遺症、服薬管理に見守りが必要 |
| 医師氏名・医療機関名 | |

つまり、**この道具の基本設計である「端末内で完結」を自ら崩す選択**になります。

確かめておきたい点を並べます。

1. **履歴がどこに、どれだけ残るか。** 消せるのか、誰が見られるのか
2. **学習に使われないことが、契約・規約で担保されているか**
3. **物理的な保管場所はどこか**（国内か、海外事業者の基盤を含むか）
4. **患者への説明と同意はどうするか。** 意見書には「意見書利用への同意」欄が
   ありますが、**それは介護認定のための利用への同意であって、
   生成AI基盤への提供に対する同意ではありません**
5. **医療情報システムの安全管理ガイドライン上の扱い**。外部の基盤に患者情報を
   出す以上、情報資産台帳とリスク評価の対象になります

なお、**源内につないでも読み取り精度は上がりません。**
源内は読み取った後の文章を扱うもので、画像を読む部分は端末側のままです。
上の「生成AIで文章を直すのは効かなかった」という実測も合わせてお考えください。

## ガバメントクラウドと、自治体システム標準化

**介護保険は、標準化の対象20業務に含まれています。**
この道具は自治体の基幹業務システムそのものではありませんが、
**読み取ったデータの渡し先が標準準拠システムになる**ので、無関係ではありません。

| | |
|---|---|
| 移行期限 | 2026年3月（令和7年度末） |
| 移行完了 | 令和8年1月末時点で 13,283システム（38.4%） |
| 経過措置 | 一部機能は令和10年度末まで。特定移行支援システムは個別設定 |

期限は過ぎていますが、**移行はまだ途上です。** これがこの道具に意味することを書きます。

1. **渡し先のデータ形式が、自治体によって違う時期が続きます。**
   旧システムと標準準拠システムが並存するので、出力先を1つに決め打ちできません。
   いまはJSON・CSV・Markdown の3通りで出せますが、
   **標準仕様に合わせた出力はまだありません**
2. **ガバメントクラウドに載せるのは基幹業務システムです。**
   この道具はその手前で紙をデータにする道具で、**端末内で完結するままでも
   成り立ちます**。クラウドに載せなければならない理由は、いまのところありません
3. **もしクラウド上に置くなら、前提が変わります。** 患者情報が端末を出る以上、
   源内の節で並べた確認事項がそのまま当てはまります

**判断の分かれ目は「誰が使うか」です。**
医療機関側で意見書を書くために使うなら端末内で十分です。
自治体側で受け取った意見書を一括でデータ化するなら、基幹業務システムとの接続を
考えることになり、そのとき初めてクラウドの話が出てきます。

出典: 総務省・地方財政審議会提出資料（2026年2月13日）、
[ジチタイワークス「自治体システム標準化の移行期限と進捗状況」](https://jichitai.works/articles/3482)、
デジタル庁「地方公共団体情報システム標準化基本方針」

## 導入前に決めておくべきこと

道具側で用意してある仕掛けと、運用で決めていただくことを分けて書きます。

**用意してあるもの**

- 元画像を破棄できる（確認が済んだら残さない）
- 匿名化加工済みデータの扱い（研究用。氏名が白抜きなら自動で判定し、住所・連絡先をマスク）
- 操作ログと利用者トークン（同じ端末を複数人で使っても履歴が混ざらない）
- 公開先の Basic 認証と、配置時に認証が外れていないかを確かめる手順

**決めていただくこと**

- 読み取ったデータを**どこに、いつまで置くか**
- 確認を**誰がするか**（医師本人か、事務か。誤りを見つけられるのは原本を見れる人だけ）
- **匿名化して使う場面と、しない場面**の切り分け
- 源内やクラウドに**出すか出さないか**（既定は出さない）
- 出す場合、**患者への説明と同意をどうするか**
- 情報資産台帳への登録と、医療情報システムの安全管理ガイドラインとの照らし合わせ

公開先の Basic 認証について一点だけ。
**作業中に `rsync --delete` で `.htpasswd` を消してしまい、一時的に認証が外れたことがあります。**
その場で戻し、以降は配置スクリプト経由にして、認証が無ければ終了コードを返すようにしてあります。

## いま言えること・言えないこと

**言えること**

- チェック欄は、整った紙なら実用に耐える水準にある（100通の正解データで 99.08%）
- データを端末の外に出さずに使える
- 効いたことも、効かなかったことも、測って記録してある

**言えないこと**

- 実データでの精度。数字はすべて合成データに対するもの
- 汚いスキャンで使えるか（文字欄 16.1%）
- 人の確認を減らせるか。**そういう道具としては作っていません**

**数字を引用するときは、必ず「どの正解データで、何を1件と数えたか」を添えてください。**

| 数え方 | 1件とするもの | 正誤の付け方 |
|---|---|---|
| 枠単位 | □ひとつ | 合っているか（0か1） |
| 質問単位 | 質問ひとつ | 答えの言葉の近さ（0〜1） |

数え方の違う数字を並べると、10ポイントの差が14ポイントに見えます（実際に一度間違えました）。
